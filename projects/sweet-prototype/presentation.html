The problem

Deployment is the first thing users do —
and the easiest place to lose them.

Before a platform can detect a single threat, someone has to deploy sensors across their infrastructure. When that first experience is confusing, customers stall before they ever reach the value they signed up for. So this is where I focused.

Who I designed for

Someone who could run this in their sleep —
in a product they've never opened.

My primary persona is a SOC analyst or DevOps engineer. Technical enough to execute a deployment, but not an expert in this specific platform. They move between many security tools every day, so they lean on familiar patterns and want to think as little as possible.

What I assumed

Design starts with a point of view.
Here's mine.

  • 1
    They don't know this UI — so it has to guide them, not test them.
  • 2
    They trust familiar, industry-standard patterns over anything clever.
  • 3
    They need confidence that everything installed correctly.
  • 4
    They want to understand exactly what protection they're getting.
  • 5
    When something breaks, they need immediate clarity on what happened and how to fix it.

The deployment flow

Five steps. One decision at a time.

1Provider 2Sensor type 3Method 4Install & connect 5Verify

Design goal

Start with the simplest question:
what am I protecting?

Visual provider cards let people recognize their environment at a glance, instead of decoding a dense form. Recognition beats recall.

[ Insert mockup ] Provider selection — visual cards for AWS, GCP, Azure, on-prem

Design goal

One decision at a time.

A single page with dozens of options creates anxiety. The wizard asks for one choice per step, so the next move is always obvious and the whole thing feels lighter than it is.

[ Insert mockup ] A single wizard step — one focused choice, nothing else

Design goal

"Installing…" tells you nothing.

So I replaced the spinner with the actual work in progress — downloading the package, installing the Helm release, connecting the sensor, validating permissions, waiting for the first heartbeat. Users should always know what the system is doing.

[ Insert mockup ] Step-by-step progress — the real work, named as it happens

Design goal

Do the hard parts for them.

Copy-ready commands. Verification in a tap. Failures written in plain language. The complexity stays inside the system, not on the person running it.

[ Insert mockup ] Install step — copy-ready Helm command, generated for you

Design goal

Say what they're getting
before they commit.

Contextual tooltips explain the visibility each sensor provides. "Deploy" becomes an informed decision instead of a leap of faith.

[ Insert mockup ] Contextual tooltip — the exact visibility a sensor adds

Design goal

Tell them how long it takes.

A simple time estimate up front. Uncertainty is what makes people walk away from a deployment halfway through — so I removed it.

[ Insert mockup ] Expected-time indicator on the deployment intro

Design goal · the one that matters most

Don't ask "did it work?"
Prove it.

The platform checks the whole chain itself — Helm release installed, pods running, authentication successful, connectivity established, first telemetry received. Protection is confirmed, not assumed.

03

Key UX decisions

The choices that shaped the design — and the reasoning behind each one.

Decision 01 · the big one

One "status" was hiding
three different problems.

A generic status forces users to interpret. I split it into three independent dimensions, so anyone can tell instantly what kind of problem they're facing.

Health

  • Healthy
  • Warning
  • Critical
  • Offline

Connection

  • Connected
  • Connecting
  • Disconnected
  • Never connected

Deployment

  • Deploying
  • Updating
  • Failed
  • Installed

Decision 02

Every problem should
explain itself.

Before

"Sensor upgrade required."

After

This sensor is running v4.7.0, no longer the latest supported release. Until it's upgraded, it may not report full telemetry or receive the latest protections.

Recommended: upgrade to the latest version · if centrally managed, roll out the updated Helm chart via Argo CD, Flux, or CI/CD · confirm it returns to Healthy and resumes heartbeats.
Upgrade sensor

Decision 03

Prove it's working
the moment it's done.

The instant install finishes, users see evidence the sensor is already protecting them — and exactly what's now in scope. Value shouldn't wait for the next login.

[ Insert mockup ] Post-install confirmation — protection scope, shown immediately

Decision 04

Make "what needs my attention?"
impossible to miss.

Active problems carry the most visual weight on the page. Attention lands where it's needed, without anyone having to hunt for it.

[ Insert mockup ] Issues prioritized visually — the problems come to you

Decision 05

Trust comes from
showing your work.

Last heartbeat, connectivity state, collected-entities summary, coverage — all surfaced in plain sight. People trust a system that exposes its reasoning instead of hiding it.

[ Insert mockup ] Details panel — heartbeat, connectivity, entities, coverage

Decision 06

The page is built for
investigation, not just monitoring.

  • →
    Sensors with issues sort to the top, automatically.
  • →
    The Issues column carries real visual prominence.
  • →
    The details panel leads with active issues, before anything else.

Trade-offs

What I chose,
and what it cost.

Overview over density

I gave the overview more vertical space, even though it pushes the table down. Seeing what matters first beat squeezing in a few more rows above the fold.

Modal over full page

A full-page flow spread the content too thin and hurt scanning. A modal fit the volume and kept users anchored in the context of the Sensors page.

Challenges

Hierarchy was the hard part.

It took many iterations to land the order: issues first, then coverage, then everything else.

  • ·
    I removed a duplicate coverage summary once I saw it stayed visible without scrolling — less noise, same information.
  • ·
    I chose not to split the details panel into Issues / Coverage tabs. The content didn't justify the extra navigation, and keeping it together made things easier to discover.

If I had more time

Where I'd take it next.

Historical coverage trends

A date selector and a trend line. If telemetry stops, the break is obvious — and easy to correlate with a deployment change.

An interactive health distribution

Click any segment of the health widget to filter the sensors table instantly. The overview becomes a control, not just a chart.

Key takeaways

How I think about design.

  • 01

    Guide people through complexity instead of exposing it.

  • 02

    Verify success — don't ask users to.

  • 03

    Build trust through transparency.

  • 04

    Every issue should explain itself and offer the next action.

  • 05

    Design for five-second decisions.

  • 06

    Reduce cognitive load by matching familiar mental models.
