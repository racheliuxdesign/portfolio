Sensor Deployment Flow

A redesign of the Sensors tab and the new-sensor deployment flow, built on the Sweet design system. Prototyped path: AWS → Kubernetes → Helm.

Open the prototype Static HTML/CSS/JS · no framework, no build step

The core insight

Users don't want to "install software" — they want coverage. The redesign optimizes for that outcome: it minimizes uncertainty, verifies connectivity automatically, and turns errors into next actions. Deployment is the first impression and the moment trust is won or lost.

Flow at a glance

1 · Provider→ 2 · Sensor type→ 3 · Method→ 4 · Install & connect→ 5 · Verification

A persistent left rail shows progress and the choices already made, so branching (AWS vs GCP, K8s vs VM, Helm vs Terraform) never feels disorienting. Each choice narrows the next — the flow, not the user, remembers the context.

Key UX decisions

  • Verify, don't ask. Instead of "Did it work?", the platform runs an explicit live checklist (release → pods → auth → reachability → first telemetry). Coverage is confirmed, not assumed.
  • Security-first credentials. The API secret is masked by default, revealed only on an explicit toggle, marked "sensitive", and rotatable. Copy actions use the Clipboard API with a fallback.
  • Actionable errors. A failure never shows an opaque code. It names the likely cause ("can't reach api.sweet.security"), and gives an ordered firewall/proxy/DNS checklist plus retry.
  • Nothing changes silently. The flow generates a command you run yourself; footer copy repeatedly reassures that Sweet applies nothing to your cluster from the screen.
  • Outcome-oriented overview. The Sensors tab leads with a coverage donut and "need attention" count — not a raw install count — matching the user's real mental model.
  • States are first-class. Empty, deploying (awaiting telemetry), healthy, updating, disconnected, and never-connected are all designed, not afterthoughts.

Trade-offs

Guided wizard vs. single page

Chose a stepped wizard for scannability and to make branching explicit. Trade-off: more clicks for experts — mitigated by a recommended default on every step and a copy-everything command at the end.

Show real secret in the command

The command is masked by default but revealable, since users must copy a working command. Trade-off between shoulder-surfing risk and utility; resolved with masking + one-time warning to store it in a secrets manager.

Auto-verification cost

Live verification adds backend work and can be slow behind proxies. Worth it: it's the single biggest driver of "installed but no data" frustration. We show an ETA and allow closing while it keeps checking.

One path implemented

Only AWS→K8s→Helm is wired end-to-end per the brief. Other providers/methods are visible but disabled with "coming soon", keeping the information architecture honest about scope.

Assumptions

  • The user is technical (DevOps/SecOps) with kubectl access and permission to install Helm charts.
  • An organization already exists; deployment happens inside it. Credentials are scoped per deployment and rotatable.
  • Health, coverage, and heartbeat data are available from the platform in near real-time.
  • The design system is the source of truth: all color, spacing, type, and components come from its tokens — nothing hardcoded.
